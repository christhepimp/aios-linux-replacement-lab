# AetherOS Lab

**Goal:** run a rooted Android / QEMU environment, get inside the Linux stack, and *gradually* replace Linux services with an AI-native operating system we design ourselves.

This is a research lab, not a finished kernel. Replacing Linux is a multi-year systems project. The repo is structured so each layer can ship independently.

Repo: https://github.com/christhepimp/aios-linux-replacement-lab

## What “the OS is an AI” means here

Not a chatbot wallpaper on Android.

AetherOS is planned as:

1. **Supervisor** — an always-on policy brain that decides *what should run next*
2. **Intent runtime** — user goals instead of app icons (`"open camera and save to notes"`)
3. **Service fabric** — replace init, package manager, and scheduler *one daemon at a time*
4. **Kernel later** — only after userspace is ours; custom kernel modules first, then a microkernel guest

You do **not** start by deleting `vmlinux`. You start by owning PID 1 in a guest VM.

## Recommended lab (rooted + real Linux kernel)

Best practical stacks in 2026:

| Stack | Root | Own kernel? | Why use it |
| --- | --- | --- | --- |
| **Android Studio AVD + custom goldfish/ranchu kernel** | Yes (userdebug / KernelSU / emuroot) | Yes | Official emulator, source kernels, ADB, QEMU gdb |
| **QEMU + Alpine/Debian guest** | Yes | Yes | Fastest path to replace init without Android baggage |
| **Waydroid** | Optional | Shares host kernel | Great Android-on-Linux, weak for replacing the kernel |
| **AVF / pKVM Linux VM on Pixel** | Device-dependent | Guest kernel yes | Real guest kernel on phone hardware |
| **Genymotion** | Often yes | Limited | Fast QA, not a kernel lab |

Primary path for this repo: **QEMU guest first**, **rooted AVD second**.

Why: an Android emulator still *is* Linux. Root lets you inspect and patch it. Replacing the kernel requires building and booting *your* image, which QEMU does cleanly.

Useful existing work to study (do not copy blindly):

- [airbus-seclab/android_emuroot](https://github.com/airbus-seclab/android_emuroot) — root Google API Play Store AVDs via QEMU gdb
- [fries/android-emulator-root](https://github.com/fries/android-emulator-root) — su + custom emulator kernels
- [tanishmeh/AVD_Rooted_Integrity](https://github.com/tanishmeh/AVD_Rooted_Integrity) — modern custom AVD kernel + KernelSU-Next
- Android Virtualization Framework / pKVM — real guest kernels on supported devices
- Waydroid — Android container on a Linux desktop kernel

## Phased plan (do this in order)

### Phase 0 — Lab boots
- Install QEMU + Android SDK emulator
- Boot a Debian/Alpine guest *and* a userdebug AVD
- Confirm root / `adb root` / `su`

### Phase 1 — Observe Linux
- Map init, zygote (Android), cgroups, binder, ashmem
- Log syscalls of one app (`strace` / bpftrace)
- Write a process inventory into the supervisor

### Phase 2 — Replace userspace, not the kernel
- Run `aios/supervisor.py` as a sidecar to init
- Intercept *new* jobs: the supervisor starts them instead of the shell
- Add an intent parser (“goal in, process tree out”)

### Phase 3 — Own PID 1 in a guest
- Custom init that talks to the supervisor
- Drop systemd/Android init for *new* services only
- Keep the Linux kernel; replace daemons

### Phase 4 — Kernel modules
- Out-of-tree module for scheduling hints / seccomp policies generated by the AI
- Still Linux. This is the first “OS is thinking” hook in kernel space

### Phase 5 — Second kernel
- Boot a tiny guest (unikernel or seL4/Zircon-class) *beside* Linux under QEMU
- Move one workload off Linux
- Only then talk about “replacing Linux”

## Quick start (supervisor prototype)

```bash
python3 aios/supervisor.py "take a note that the lab is alive"
```

This is the AI OS *idea* in userspace: intent → plan → processes. The kernel stays Linux until Phase 5.

## Honest limits

- There is no drop-in “replace Linux with AI” binary. Anyone selling that is lying.
- Android’s userspace (Bionic, Binder, ART) is not GNU/Linux userspace. Plan for both.
- Root on an emulator is for research. Do not use this to hide malware or bypass device integrity on other people’s machines.
- A real AI kernel needs formal isolation. The supervisor must not be an unconstrained model with `root` and a dream.
